# Dreame Home beta

This component discovers Dreame Home account devices and exposes successful telemetry as sensors and binary sensors. Exact L9 definitions supply source-backed names, enums, units and named controls. Beta `0.3.0b2` targets Core 2026.9.4 or newer and adds cycle-progress/elapsed-time sensors, corrected dryer time metadata and recurring known-property retries. It retains the 16 washer controls, 12 dryer controls and native L10s Ultra Gen 3 vacuum entity introduced in `0.3.0b1`.

A user confirmed the earlier `0.2.0b3` telemetry beta's installation and updating values; its diagnostic confirmed all three devices online and MQTT-connected. A later `0.3.0b1` diagnostic was downloaded after the laundry cycles ended. Both laundry devices reported power off with retained old values; this does not demonstrate a running-cycle failure. Accepted control writes have not been established by the supplied evidence. See the [control guide](https://github.com/Ampersandman/Dreame-Home/blob/main/docs/appliance-controls.md), [historical diagnostic review](https://github.com/Ampersandman/Dreame-Home/blob/main/docs/ha-diagnostics-review.md) and [latest review](https://github.com/Ampersandman/Dreame-Home/blob/main/docs/ha-diagnostics-review-2026-10-06.md).

Install through HACS by adding `https://github.com/Ampersandman/Dreame-Home` as a custom repository with category **Integration**, downloading **Dreame Home**, and restarting Home Assistant. See the [HACS installation guide](https://github.com/Ampersandman/Dreame-Home/blob/main/docs/ha-os-installation.md). The API is included under `api/`; HACS needs no separate client package or release asset.

Historical live EU cloud validation succeeded for these appliances. This earlier capture used the 15-property vacuum baseline. The counts below describe distinct property coordinates observed through addressed reads and MQTT, rather than the number of Home Assistant entities or every possible operating state.

All three appliances connected to MQTT with verified TLS. The final dryer read returned 23 successful property codes and 20 non-null values: `3.11`, `5.1` and `4.7` were null. Earlier MQTT supplied values for `5.1` and `4.7`, leaving 22 distinct non-null observations overall. Only `3.11` has never supplied a non-null value. Null RPC replies preserve earlier successful MQTT values without advancing their freshness; `last_reply_null` distinguishes the latest reply from retained state. The app's conflicting `3.11` subscription and `3.13` night-mode control remain distinct. The observed `3.13` receives its exact UI name, while unknown `4.7` keeps a neutral label.

The recurring washer and dryer plans reserve 24 and 17 coordinates used for reading or notifications by their exact app plugins. Source write-only fields are excluded from those seeds. Additional successful observations, including MQTT reports of such fields, can create entities and become eligible for later property reads. Known candidates and previously valued exact-model addresses remain retryable after null, empty or failed replies. This fixes a one-shot-read starvation case; it does not diagnose a failure in the post-cycle snapshot. Cloud-online gating, per-device locks, cooldowns and the 240-address budget remain in place. Unknown models receive only successful observed addresses. Failed responses and previously unobserved null values do not create entities. Enum labels use explicit property mappings; unknown codes and inferred Boolean conversions retain their raw scalar values. The original enum code remains in the `raw_code` attribute.

Both exact L9 schemas also identify the cloud userdata key `prop.s_auto_upgrade`. The component fetches this setting at discovery cadence and names its read-only sensor **Automatic firmware updates** when a value is returned. Its wire strings `'0'` and `'1'` remain unchanged. Missing values produce no default or cloud write, and a setting read failure does not make appliance telemetry unavailable. This additional HTTP setting path still needs live acceptance separate from the successful property/MQTT capture.

The current vacuum seed contains 22 candidates: the earlier 15-property baseline, five control-context properties and progress candidates `4.63`/`4.64`. The later diagnostic contains 167 vacuum property rows, with 145 source-mapped coordinates and 22 neutral coordinates. Neither progress coordinate is present; source-backed read candidates are not proof of firmware acceptance. A successful `3.1` supplies battery state. Cleaning time `4.2` uses minutes and cleaned area `4.3` uses square metres. Other successful coordinates, cached keys, actual Boolean values and supported compound JSON leaves receive stable entities. Unknown addresses keep neutral coordinate labels. Structured roots retain ordinary arrays, while dictionary leaves and uniquely keyed setting lists can expand into stable entities.

Both exact L9s now expose derived **Cycle progress** in percent and **Elapsed cycle time** in minutes, alongside existing **Program duration** and **Remaining time** entities. Washer timing uses `2.12`/`2.13`; dryer timing uses `2.9`/`2.11`. Existing property identities are preserved. Derived values require successful current replies no more than 180 seconds old, recognized powered cycle context and valid reported durations. Powered-off, stale or invalid context stays unknown; the washer's fresh phases 5/6 represent washing completion at 100%, not appliance shutdown. These are estimates and can move backward when the appliance revises its duration. See [cycle sensors](https://github.com/Ampersandman/Dreame-Home/blob/main/docs/cycle-progress.md) for formulas, exceptions and provenance.

After the restart, add **Dreame Home** under Settings > Devices & services. Choose the region used by the app; the validated region is `eu`. Enter credentials locally in the setup form. Setup stores the username, region, account identifiers and refresh token, persists token rotation, and supports reauthentication. It does not persist the password or access token. Home Assistant's configuration storage is not encrypted by this integration.

MQTT is optional in the setup form. Without it, metadata and addressed property reads remain available. Discovery runs every ten minutes; property reads run approximately once a minute. Cloud-reported online state and MQTT connection state have separate entities. The cloud online flag may lag physical power changes by up to ten minutes, and a broker connection alone does not establish current appliance state. Per-device read failures remain separate from account discovery failures.

Compound expansion is bounded to 256 leaves per property, and polling is bounded to 240 addresses per refresh. Root entities for structured values are disabled by default; enable one in the entity registry to inspect its redacted `raw_value` attribute. The backend retains the original value privately. New MQTT coordinates create entities dynamically. Unknown messages remain in the bounded observation store and produce a redacted `dreame_home_message` event. Diagnostics omit unknown text values, credentials and raw account envelopes.

Named laundry switches/selects and start/resume, pause and stop buttons use exact encoders: 13 washer writable property coordinates and 9 dryer coordinates, plus 3 buttons on each. Laundry stop powers off. The native vacuum offers start, pause, stop, return to base and fan speed. Controls need a present/online device, successful account update and successful required observations no more than 180 seconds old. Missing, null, failed, unknown or stale context disables affected controls. Program restrictions, network authorization, child lock and fault/status checks remain enforced. The component never predicts results, replays uncertain commands or automatically calls `reportAll`. Diagnostics separate supported commands from currently available commands; an unavailable control is not an unsupported model. Ambiguous settings, number controls without full bounds, typed events and maps remain omitted; see the [control guide](https://github.com/Ampersandman/Dreame-Home/blob/main/docs/appliance-controls.md), [live coverage](https://github.com/Ampersandman/Dreame-Home/blob/main/docs/live-coverage.md) and [roadmap](https://github.com/Ampersandman/Dreame-Home/blob/main/docs/home-assistant-roadmap.md).

The backend includes notices for MIT-licensed extraction from Tasshack/dreame-vacuum and corroborated pagination from TA2k/ioBroker.dreame. Exact L9 metadata comes from pinned model-specific app plugins. The EU broker uses a CA recovered from a signature-verified Dreame Home APK; hostname and certificate-chain verification remain enabled.

GitHub's Python 3.12/3.14 offline checks and official HACS/hassfest validators passed for earlier published revisions. Historical HA evidence confirms initial telemetry/MQTT operation on Core 2026.9.4 / Python 3.14.6; the later post-cycle snapshot expands vacuum coverage. These findings do not validate `0.3.0b2` cycle sensors, accepted writes or the two new vacuum progress reads. Accepted controls, fresh running-cycle comparisons, reload/unload, reauthentication and recorder behavior still need acceptance.
